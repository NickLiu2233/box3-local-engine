# 从源码完成首个作品

这份教程使用本机源码开发栈，完成服主初始化、创作授权、简单地图、脚本、工程备份、发布与两名玩家游玩。你会自行创建内容，不需要下载其他地图或模型。桌面发行和服务器包使用自己的数据目录，操作入口相似但端口与配置以管理器显示为准。

## 1. 启动前配置服主令牌

按[开发入门](./developer-guide.md)准备 Node.js `22.17.x`、Docker Compose v2 并启动 Docker。在仓库根目录安装依赖、复制配置：

```sh
npm run install:all
cp .env.docker.example .env
```

已有 `.env` 时跳过复制。PowerShell 使用 `Copy-Item .env.docker.example .env`。随后生成一个仅供本机开发使用的随机令牌：

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

将输出保存到本机根 `.env` 的 `BOX_PLAY_ADMIN_TOKEN=` 后，不加空格，也不要保留模板中的空值。例如下面只展示字段，不能把占位符当作令牌：

```dotenv
BOX_PLAY_ADMIN_TOKEN=<your-generated-development-token>
```

服主入口要求至少 16 字符；开发脚本不会自动生成这个值。它与 Linux Web 管理器的 `BOX_SERVER_MANAGER_TOKEN`、服务端 `BOX_PLAYER_AUTH_API_KEY` 是不同密钥。不要提交 `.env` 或公开令牌。源码栈已运行时，停止并重启，让所有服务读取同一个值。

```sh
npm run check:workspace
npm run dev:infra
```

这个终端持续运行。等待 Player Service 成功连接数据库、各服务就绪。若使用已有开发 PostgreSQL，在 `.env` 配置宿主机可访问的 `BOX_DATABASE_URL` 并改用 `npm run dev`。默认本机地址是 Creator `3127`、Play `3121`、VOXA `3123`、Player Service `3124`、登录门户 `3125`、玩家后台 `8000`。

## 2. 创建玩家并初始化管理员

1. 浏览器打开 `http://127.0.0.1:3125/`，注册一个开发玩家账号，记作玩家 A。只使用测试资料与独立密码。首次没有账号时，服主登录仍使用令牌，不需要先有玩家管理员。
2. 打开 `http://127.0.0.1:8000/`，切换到“服主登录”，把上一步配置的令牌填入“服主管理令牌”，点击“登录后台”。出现“服主管理功能未开启”时检查根 `.env`、长度和是否已重启；不要反复注册账号解决此错误。
3. 进入“创作管理 → 创作权限”，点击“新增”，从已注册玩家中选择玩家 A；打开其管理弹窗，开启“启用创作端”。为本教程保留新建地图、编辑地图、导入工程、导出工程和管理模型能力。开关与能力选择直接保存，不需要修改数据库。
4. 如果需要日常管理账号，进入“服主管理 → 权限组”，新增一个权限组，选取工作需要的能力；再进入“管理账号”，新增独立用户名、显示名称和至少 12 位初始密码，并选择刚才的权限组。退出后可用“管理员登录”验证它只看见获授权页面。

普通注册玩家、创作者与后台管理员是独立身份。不要把玩家 A 的登录密码填到“管理员登录”；也不要分发服主令牌给每个协作者。单人开发可以继续用 owner 完成本教程，但日常管理应使用有范围的管理账号。

验证过可选管理员账号后，切回“服主登录”继续本教程后面的后台操作，避免刚创建的权限组没有游玩包导入能力而卡住后续步骤。

## 3. 新建小地图

使用玩家 A 的登录浏览器打开 `http://127.0.0.1:3127/projects`。若提示未授权，回到后台确认给正确玩家开启了创作端，刷新或重新登录。整个教程统一使用 `127.0.0.1`，不要混用 `localhost` 导致 Cookie 不一致。

在“地图列表”点击“新建作品”，输入名称“我的首个本地作品”、作者和简介，选择“小（32×32×32）”，确认创建。点击新地图卡片进入编辑器，等待地形与资源载入。使用默认新工程即可先完成运行流程；在编辑器“创建”工具中自行放置少量体素，便于辨认本作品。不要先导入历史地图包，否则会混入不必要的账号、脚本或资源状态。

地图卡片“更多操作 → 编辑信息”中可以查看永久地图 ID 并修改访问 ID。记下永久 ID 用于排障；访问 ID 只是 URL 名称，两者不能互换。

## 4. 加入一段服务端脚本并预览

在编辑器点击“脚本”，选择服务端入口 `index.js`，将下面代码放入该入口。不要放到客户端 `clientIndex.js`，也不要只新建一个未被入口调用的辅助文件。

```js
console.log('首个作品：服务端脚本已启动');

world.onPlayerJoin(({ entity }) => {
    world.say('欢迎来到我的首个本地作品');
    console.log('玩家加入', entity.player.name);
});
```

`world.onPlayerJoin` 是玩家加入事件，`world.say` 向游戏聊天发送文本，`console.log` 写入脚本日志；接口来自仓库脚本声明，不是浏览器 DOM API。本例不使用地图管理或封禁能力，不需要额外签发地图授权。

点击编辑器右上角运行按钮。脚本修改会在启动运行时保存并重新执行；若已在运行，先停止再运行。应能进入预览并看到欢迎消息，日志中有启动文字和玩家加入记录。停止运行后回到编辑状态。还可通过 Creator 的 `/p/<project-id>` 进行本地预览，其中 `project-id` 与编辑地址 `/e/<project-id>` 使用同一个工程 ID；它仍来自可编辑工程，不表示已发布到 Play。

如果脚本出错，先看编辑器错误位置和源码栈运行时日志；修正后再次停止、运行。此时普通地图内容仍由服务器维护，客户端 UI 的显示权限不代替服务端校验。

## 5. 自制一个模型（可选）

在地图编辑器“模型”中选择“项目模型库”，点击新建模型打开嵌入的 VOXA。在 VOXA 内选择“体建造”（Build Box）工具画一个简单方块，取一个容易识别的名称，然后点击“保存”，等待保存结束后返回地图。模型应出现在项目模型列表；选择它，在场景中放置并再次运行，检查模型可见。

这个步骤使用你自己画的几何内容，没有外部下载素材。保存是必需的：只有模型名称而没有保存的工程与 mesh，不能验证发布资源。也可从 Creator“模型列表 → 新建模型”建立本地模型库项目，保存后再加入地图；独立模型库与地图中的项目模型有不同范围，不能只凭库中有卡片就判断作品已经引用了它。

若 VOXA 提示缺少“管理模型”权限，回后台给玩家 A 授权；如果模型服务未运行，检查源码栈的 voxa 日志和 `3123` 端口。本步骤可独立验收，不是后面验证地图包所必需的外部资产。

## 6. 备份可编辑工程并测试恢复

回到 Creator 地图列表。主地图卡片选择“更多操作 → 导出 → 导出地图组工程”，保存下载的 `.boxproject` 到仓库外的备份目录。只有一张地图时也可“导出本地图工程”；多地图组备份必须选择地图组，避免遗漏副地图。

为验证备份可读，点击“导入工程”，选择刚下载的文件，在“选择工程归属”中选择“作为独立地图组”，点击“开始导入”。等待成功后打开新导入的地图，检查体素、服务端脚本和可选模型，并重新运行。导入会处理标识冲突，不要手动覆盖原工程目录，也不要为测试恢复先删除原作品。

确认恢复后继续使用原作品发布。备份文件可能包含你的源脚本和作品数据，应像自己的作品文件一样保管；`.boxproject` 不包含玩家身份数据库。

## 7. 导出游玩包并导入 Play

在原主地图卡片选择“更多操作 → 导出 → 导出游戏包”。首次版本使用 `v1.0.0`，填写更新说明，选择“仅本地资源”，点击“开始导出”，保存下载的 `.boxplay`。再次导出相同作品时使用新的版本号，不可覆盖不可变版本。

“仅本地资源”携带这次地图组所需资源，不要求你设置 OSS。`.boxplay` 包含主地图与副地图的发布快照，不含可继续编辑的 `source/`；之后修改 Creator 工程不会自动更新已经导入的包。

回到玩家后台，进入“游玩管理 → 游玩地图”，点击“导入游玩包”，选择 `.boxplay`。在“检查游玩包”中确认地图数量、版本、脚本和媒体，点击脚本可预览内容；此预览不会执行脚本。确认内容来自自己的作品后点击“确认导入”，等待“已导入”提示。

在已导入地图行检查地图组开关是“开放”。需要易记链接时通过“设置”修改“访问 ID”，例如 `first-local-map`；如果冲突使用其他名称。确认后打开 `http://127.0.0.1:3121/p/first-local-map`，或使用界面提供的实际游玩链接。不要把 Creator `3127` 的地址发给玩家。

## 8. 用两名玩家验收

先让玩家 A 进入 Play 地图，检查欢迎消息、体素和模型。再使用另一浏览器或独立浏览器配置文件，在 `http://127.0.0.1:3125/` 注册玩家 B，然后在同一个配置文件中打开相同 Play 链接。玩家 B 不需要 Creator 或后台权限。

两个窗口同时进入同一地图公共实例，应能看到彼此移动；源码运行时日志应记录两次加入。用普通玩家 B 打开后台不能自动获得管理会话。若两窗口表现成同一玩家，检查是否共享了 Cookie；两个普通标签页不是两个独立登录环境。

本机源码默认只监听回环地址。跨电脑测试需要另行配置可信局域网地址、公开 URL 和允许来源，不能仅把 `127.0.0.1` 发给另一台电脑；不要为这个本机教程开放 Creator 到公网。

## 9. 重启与完整数据备份

关闭预览和玩家窗口，在源码栈终端按 Ctrl+C，再运行 `npm run dev:infra`。确认工程仍能编辑、Play 地图仍存在、两个测试玩家仍可登录。这验证持久化，不要求删除 Docker 卷。

`.boxproject` 验证了作品恢复；完整部署恢复还需要身份数据库。下面只针对 `dev:infra` 的默认开发数据库（账号 `box`、库 `box`、身份 schema `box_identity`），使用 PostgreSQL 容器已有工具。先在源码栈终端按 Ctrl+C，保持 PostgreSQL 容器运行，避免继续写入。已有外部数据库或修改过账号/schema 时，改用实际连接和对应的 `pg_dump`/`pg_restore`，不要直接复制默认参数。

在仓库根另开终端执行：

```sh
docker compose --profile infra exec -T postgres pg_dump -U box -d box -Fc -f /tmp/box-first-project.dump
docker compose --profile infra cp postgres:/tmp/box-first-project.dump ../box-first-project.dump
docker compose --profile infra exec -T postgres createdb -U box first_project_restore
docker compose --profile infra exec -T postgres pg_restore -U box -d first_project_restore --no-owner --exit-on-error /tmp/box-first-project.dump
docker compose --profile infra exec -T postgres psql -U box -d first_project_restore -c "SELECT COUNT(*) FROM box_identity.users;"
```

这会在仓库外保存二进制备份，并恢复到新的 `first_project_restore` 测试库，保留原库与开发配置。恢复前该库名应不存在；如果已有同名库，选择新名称并同步替换后三条命令，不能删除不明用途的数据库。最后的用户数量应包含你创建的玩家 A/B。命令采用容器文件与 `compose cp`，避免 PowerShell 文本重定向损坏二进制归档。真正迁移时还需配置恢复库的连接串、重启业务并验证登录和权限，不能只看归档文件存在。

需要停止基础服务时执行：

```sh
docker compose --profile infra stop postgres redis
```

管理器的数据备份归档主要覆盖作品与本地资源，不能代替外部数据库备份，也不能把源码目录备份直接当成桌面运行目录使用。

保留以下材料在仓库外：可编辑 `.boxproject`、发布 `.boxplay`、数据库备份、私密 `.env` 和本机新增模型资料。记录引擎提交/版本和实际配置。导入归档或恢复数据库前先保留现有数据；日常故障不要执行 `docker compose down -v`。

## 完成后应能说明

你应能区分 owner、管理账号与玩家，知道谁授予 Creator 权限，解释 `.boxproject` 与 `.boxplay` 的用途，并从两个独立玩家会话连接同一发布快照。修改实现前继续读[架构指南](./architecture.md)与[测试指南](./testing.md)。若某一步失败，记录执行命令、服务首个错误、系统/架构和引擎提交，先移除令牌与个人资料，再提交普通 Issue。

# 引擎核心性能评估与优化计划书

> 设计/规划资料，不保证全部能力已实现。操作步骤以当前使用指南与源码为准；版本状态见[当前说明](./current-status.md)。

日期：2026-10-07。评估基准：工作区提交 `d9be844e`。

本轮仅进行源码审查与算法资料核对，只新增本计划书，没有修改运行时代码、配置或用户地图。本报告是实施前评估，没有运行代表地图、采集 CPU/GPU trace 或执行性能基准；因此不宣称已经找到实测最大瓶颈，不承诺未经测量的提升百分比。

## 1. 整体判断

**建议保留现有引擎架构，优先减少重复工作与突发工作，再按测量结果优化算法。** 当前已有体素网格 Worker、粒子 Worker、体素可见性图、视锥剔除、LOD、碰撞空间树、TypedArray 和对象池，WebGPU 还有 Render Bundle 缓存。基础优化并非空白，全面重写风险高且缺少收益依据。

流畅度应以帧时间尾部、输入响应和模拟稳定性为核心。平均 FPS 好看，仍可能在挖方块、转视角、网络纠正、模型加载时卡顿。客户端渲染、预测物理与服务端权威模拟必须一起评估；降低绘制成本不能解决服务端 tick 延迟。

当前最值得优先验证的四条链路：

1. **体素可见性存在与整张地图块数相关的每帧清零开销。** 即使只看见小区域，也可能付出全图规模的初始化成本。
2. **物理求解在多个层次重复执行，且每次重建碰撞树。** OBB 子步、位置纠正、客户端重放和客户端插值会放大单次求解成本。
3. **体素 Worker 成批产出，主线程立即接收并更新 GPU 资源。** 计算移到 Worker 后，上传尖峰仍可能拖慢帧率。
4. **测量数据存在明确的统计问题。** 先修正统计并建立基准，才能判断算法是否改善流畅度。

以上是代码证据支持的优化候选。最终优先级由代表场景的分阶段耗时和尾部帧时间确定。

## 3. 先建立可靠的性能基准（P0）

### 3.1 两项明确的统计问题

- `services/game-server/src/index.ts` 的 `_tick` 中，`maxTickTime` 使用 `Math.min` 更新，无法表达最大 tick 耗时。后续应修正并确认初始化和统计窗口。
- `apps/game/src/engine/profile/profiler.ts` 忽略 FPS 数组中的零样本，但平均值仍除以固定 512；未填满窗口时平均 FPS 会偏高。后续应按有效样本数计算，并明确 `deltaClock` 的时间口径。

这些是静态代码可确认的问题，本轮未修复。现有客户端 perf 主要是帧间隔与网络消息统计，服务端有 tick 汇总；不足以区分 broad phase、narrow phase、solver、重放和上传耗时。

### 3.2 测量方式

建立独立的客户端、Worker、服务端采样记录；同一次回放以场景 ID、tick、帧序号关联，不能直接比较不同进程的原始时钟。使用单调时钟，统计采样开销，先对比关闭和开启采样的结果。

客户端记录：rAF 帧间隔、poll、预测/重放、模型/动画、可见性、上传、绘制提交、overlay；同时记录长任务、GC、堆内存和输入到呈现的延迟。GPU 使用异步计时，按阴影、不透明、透明/流体、粒子、后处理分 pass 统计。WebGL 的不支持或 disjoint 样本标为不可用；WebGPU 计时能力缺失时使用浏览器 trace，不能把 CPU 命令提交时间当 GPU 执行时间。

物理记录：总刚体、active/fixed/真正静态数量、实际求解次数、重放次数、树构建耗时、节点访问量、候选对、有效接触、地形查询、约束求解耗时。记录每个 tick 是否含位置纠正，区分预测和实际求解。

资源记录：Worker 排队时长、每批块数、生成时长、待上传字节、上传耗时、结果版本、Bundle 命中/重建数、资源创建/释放量。服务端记录 tick P50/P95/P99、事件循环延迟、脚本耗时与积压，而非只有平均值。

### 3.3 固定测试矩阵

| 场景                     | 用途                          | 参数                                  |
| ------------------------ | ----------------------------- | ------------------------------------- |
| 小地图常规游玩           | 防止小场景因复杂优化变慢      | 固定镜头路线、玩家输入、资源版本      |

### 3.4 建议验收目标

目标是拟定门槛，需在 P0 固定硬件与场景负载后锁定，不是现有引擎的性能保证。

- 标准档以稳定 60 FPS 为目标：帧间隔 P95 ≤ 18ms、P99 ≤ 25ms；若硬件只能承担 30 FPS，应单独设置 30 FPS 档位和约 33.3ms 的预算。
- GPU 与客户端 CPU 工作都留余量，60 FPS 档初始以各 ≤ 12ms 为工作预算；两者会流水并行，不能简单相加或认为阶段分位数可直接相加。
- 固定普通游玩回放不新增超过 50ms 的卡顿；地形集中修改场景，超过 50ms 的卡顿次数以基线为参照显著减少。
- 服务端 tick P99 初始目标 < 32ms，明显低于 64ms tick 周期；同时验证真实调度和脚本链路，不因 tick 计时范围漏采而误判。
- 主攻场景的 P99 或主要耗时至少改善 15%，且超过运行间波动；常规场景不允许可重复的 >5% 性能回退。具体门槛在基线完成后调整并冻结。
- 相同输入的碰撞、事件、位置误差和输入响应满足既有行为契约；30 分钟资源无持续无界增长。质量或负载不同的结果不能当作同等算法收益。

## 4. 具体优化候选与算法依据

### P1-A：体素可见性初始化与更新范围

**依据：** `bfsClear` 当前对全图块规模清零。设全图块数为 N、视锥候选块数为 V，当前至少有 O(N) 清零，再做范围扫描和 BFS。大地图小视域场景是最容易辨别的实验。

**方案：** 先比较 TypedArray.fill 与现有循环，只作为低风险常数优化；若清零占比仍高，采用访问代数标记或 touched-list，只初始化当帧触及的节点。期望初始化从 O(N) 向 O(touched) 转移，而非宣称整个可见性算法变成 O(1)。适度保留数据布局，减少重写 BFS。

第二步再评估缓存：相机/投影不变、地形连通性版本不变时复用；相机旋转、移动、传送、窗口变化、地形开洞均必须失效。不能只判断相机所在 chunk 是否改变。访问代数溢出需完整清理；地图重置和尺寸变化要重建状态。

**验证：** 固定视域逐步扩大地图尺寸，观察可见性耗时曲线；新旧实现逐帧比较可见块集合，并覆盖边界视角和开洞。剔除不得漏掉应显示内容。

### P1-B：体素生成与 GPU 上传错峰

**依据：** dirtyChunks 整批连续处理、UPDATE_CHUNK 即刻上传。优化目标是减小峰值，而非假设 Worker 算法本身低效。

**方案：** 主线程增加有界上传队列，以时间和字节预算调度；近处可见块优先，远处低优先级块渐进更新。Worker 保留 dirty 去重，同时分批处理并定期让出消息处理机会。按 chunk ID 与版本合并尚未执行的旧结果，防止旧网格覆盖新状态。

建议初始上传时间预算 1–2ms/帧，再由测量调整。必须设置队列字节上限、背压和最大等待时间，避免“每帧更快但积压无限”。Transfer 缓冲区只能在上传 API 完成所需的数据读取后回收；不得提前归还造成数据被覆盖。

**验证：** 比较地形修改场景 P99、上传峰值、近处可见更新延迟和队列峰值。碰撞更新与可视网格延迟要有明确语义；不能延后权威碰撞判定或让玩家踩入尚未正确呈现的地形。

### P1-C：静态碰撞索引复用

**依据：** 每次 findContacts 重建 fixed 树；同一 netTick 的多次子步重复付费。时间相干性允许复用未变化的空间索引。动态树也可增量移动代理，但不是所有场景都胜过批量构树。[Box2D 动态树接口](https://box2d.org/documentation/group__tree.html)提供移动代理与局部重建机制，可作为设计参考。

**方案：** 将真正不动的 static 与 fixed-but-moving/animated/kinematic 对象分开；只对真正静态集合建立长期索引，通过新增、删除、变换、碰撞组变化等版本失效。动态集合第一阶段保留现有批量构树；第二阶段以不同分布测试增量 BVH/refit，必要时定期重建。

必须先改变缓存的所有权设计：当前 NODE_POOL/BOX_POOL 是全局临时池，会被清空、复用；不能直接把现有 fixed 树引用跨 solve 保存。树中的 `id` 也是内部数组索引，集合重排后会失效。预测克隆状态、实际状态、客户端和服务端都要隔离缓存生命周期。

**复杂度预期：** 消除未变化静态集反复构建的成本；增量树维护取决于变化数 M、树质量与重叠分布，不能保证最坏情况。密集重叠时真实候选对 K 可达 O(N²)，任何空间索引都不能消除必须处理的 K。

**验证：** 候选接触对与旧算法一致、玩家查询不漏碰撞；动态移动平台、删除实体、回放、传送、碰撞组变更均正确；树质量退化时有重建阈值。

### P1-D：静态模型数据与资源加载去重

**依据：** 每帧重建模型列表；`getRenderableMesh` 有 in-flight 占位，而 `getRenderableTexture` 在 imageIndex 未填入时会再次触发 retrieve，应检查下层是否已经去重。

**方案：** 缓存静态模型变换、法线矩阵和可复用解析信息，按变换、材质、动画、受伤效果及资源版本失效。大量实体时测试模型空间索引，先查询视锥候选，再做精确剔除；小场景保留线性扫描路径。确认下层加载行为后再决定是否统一 in-flight Promise、失败重试与回收。

**验证：** 区分 models 遍历、动画和 light probe 等阶段；比较有大量静态实体的场景。不要缓存依赖相机的距离排序结果，也不要冻结移动模型或受伤反馈。

### P2-A：物理整岛休眠

**依据：** 当前速度截止未将静止动态体移出主要求解路径。将动态刚体和接触视为图，连通分量整体低能量且持续稳定后进入 sleep，能把求解规模从全部动态体缩小到醒着的体和相关接触。整岛唤醒对于堆叠正确性很重要。[Box2D Simulation Islands](https://box2d.org/posts/2023/10/simulation-islands/)明确讨论这一机制。

**方案：** 首先统计“低速但仍求解”比例，再决定是否实施。设计独立 sleep 状态，保留睡眠体的碰撞代理；玩家接触、移动平台、外力、区域力/浮力改变、脚本变换、地形变化均需唤醒关联岛。复用图结构前，审查现有 lock-island 的用途，不混用网络锁定和休眠。

**风险：** 新持久状态可能需要 schema、快照和网络协议兼容策略；碰撞事件语义、回放与浮力不能丢失。不能按相机距离关闭物理，也不能只令速度为零就跳过对象。

**验证：** 堆叠长期稳定、连锁推动立即唤醒、平台支撑正确、事件契约一致；对全体移动场景检查管理开销是否反而变大。

### P2-B：网络预测和重放预算

**依据：** 常规路径有 frameNetTicks 预算，但动态公式可能增大；skip/frameskip 分支设置 Infinity。重放会重复状态 assign 与 netTick，插值还单独求解。因此帧预算要统计真实求解次数和累计毫秒，不能只看配置默认值 2。

**方案：** 基线完成后，为正常预测、回放追赶和恢复分别设计预算；使用 tick 数和时间双重保护。历史状态可评估环形缓冲，减少 forgetClientNetStates 的搬移，但当前窗口只有 16 tick，这属于次级常数优化。先测复制耗时再考虑差量快照或受影响集合计算。

**风险：** 预算触顶时必须明确定义保持最近完成状态、权威重同步与视觉纠正策略，避免积压、输入延迟和反复 snap。物理结果不能依客户端性能随意减少精度；局部预测只有在证明碰撞依赖闭包完整后才能采用。

**验证：** 网络抖动、恢复前台、传送、多人纠正；同步误差、回放积压、输入到画面延迟和 P99 一起验收。权威服务端不得丢弃必要模拟步骤来追求客户端帧率。

### P2-C：渲染提交、阴影与 GPU 像素成本

**依据：** GL 已有距离排序；GPU 已有 Bundle Cache，因此先判断是 CPU 提交瓶颈、顶点瓶颈还是 fill rate 瓶颈。[MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)建议减少绘制批次、控制分辨率并避免阻塞查询。

**方案：** 高重复 mesh/material 的不透明模型测试真正 instancing，减少 draw 数；按照资源兼容性分组，动画、GLTF 与透明模型分别处理。Bundle key、资源版本和释放机制需要一致性检查，不能把命令缓存命中视为 GPU 工作减少。

阴影分开测静态与动态 caster，评估静态层缓存及远级联较低更新频率；复用现有烘焙/dirty 机制。相机、光照、caster 和资源变化需失效。透明保持当前顺序语义，不能直接套用不透明材质分桶。

若 GPU 像素耗时主导，采用独立流畅档：渲染分辨率、阴影与昂贵后处理自适应，UI 保持清晰。分辨率缩为 0.8 时像素量约为 0.64，仅表示像素工作量推导，不等于总帧耗时下降 36%。使用平滑窗口、上下阈值与冷却时间防止画质来回跳。

GL rAF 末尾显式 flush 可做独立 A/B 检查；flush 本身不等于 CPU 等待 GPU，不能把它直接认定为卡顿来源。异步计时也不能引入 readPixels/finish 等同步等待。

**验证：** 近远层阴影、透明交叠、流体、动画、切换资源均无错误；算法收益在相同画质下比较，画质调节收益单独列出。

### P3：网格合并、接触缓存与多线程大改

- **体素 greedy meshing：** 若顶点/带宽确实主导，可合并材质、面方向、光照/AO、透明规则等兼容面。地形当前有逐面数据格式和 LOD 前缀排序，合并必须兼容 shader、UV 和 LOD，平整墙面与随机材质分别测试；不能直接替换网格器。网格生成仍须扫描输入，改善主要来自输出几何减少。
- **接触持久化 / warm starting：** 若 solver 或接触生成显著占比，再设计按稳定实体与接触特征 ID 的缓存，跨步复用冲量；已有 contact 每次清理，不足以据此认定所有内核都完全没有复用。参考 [Erin Catto 约束求解讲义](https://box2d.org/files/ErinCatto_ModelingAndSolvingConstraints_GDC2009.pdf)。必须处理子步 dt、法线变化、回滚与缓存失效。
- **物理 Worker/WASM：** 仅在前述优化后 CPU 仍超预算时评估。成本包括状态传输、同步、输入延迟与维护两端语义；现有求解器依赖模块全局数组和临时池，直接并发不安全。先明确独立 world/context，再考虑并行。
- **粒子、音频、脚本、UI：** 根据分阶段数据处理热点。粒子已有 Worker 和上限，重点测屏幕 overdraw；音频检查活跃节点与解码；脚本检查超时与任务积压；UI 检查布局/绘制。降低频率仅适用于允许延迟的展示任务，伤害、奖励、碰撞事件不纳入降频。

## 5. 推进顺序与每阶段交付

| 阶段          | 工作                                                      | 进入下一阶段的条件                       |
| ------------- | --------------------------------------------------------- | ---------------------------------------- |
| A：基准       | 修正统计、补分阶段采样、固定地图回放与测试设备            | 取得 CPU/GPU/物理/上传基线，明确前三热点 |
| B：低风险优化 | 优先实验可见性初始化、上传队列、资源去重、静态数据缓存    | 单项 A/B 可复现改善，正确性检查通过      |
| C：物理索引   | 静态/运动学分类、缓存所有权、静态树复用；动态树择优       | 候选对与旧算法一致，多种分布均验证       |
| D：深度优化   | 根据数据选择休眠、实例绘制、重放预算或阴影策略            | 达到固定目标，无玩法与尾部性能回退       |
| E：集成验收   | 全矩阵、长时间运行、GL/GPU、客户端/服务端、最终发行运行时 | 工程检查及最终镜像测量通过，保留回滚方案 |

工作量按热点证据再拆分，不在无测量时承诺工期。每个实验单独开关、单独结果记录，一次只改变一个主要变量；通过后再组合测试。物理方面优先优化索引与数据搬运，保持子步、迭代和 tick 频率，之后才评估需要改状态模型的方案。

每项结果报告包括：固定输入与环境、前后 P50/P95/P99、阶段耗时、内存、正确性结果、画质差异、失败场景与回滚开关。物理需要差分回放和压力验证；上传/缓存需要生命周期验证；仅文档变化不运行全量引擎测试。本轮没有执行这些未来实验。

## 6. 实施约束

1. 不凭经验直接换物理库、改渲染后端或重写主循环。
2. 不以降低权威 tick、OBB 子步或约束迭代作为首批优化。当前 ACTIVE_ITER_COUNT 已为 2，进一步减少尤其需要稳定性证明。
3. 不用视野剔除替代物理判定，不按客户端帧率改变权威结果。
4. 不盲目扩大对象池和长期缓存；节点池、MAX_BODIES = 3500 等容量边界需压力验证及明确越界策略。
5. 涉及 schema/协议/事件契约的改动必须有兼容性回归；性能实验与版本兼容变更分别审查。
6. 依工程规范完成最终 `rush verify`；涉及运行时行为还需验证最终镜像，不能只以宿主机源码测试作为发行依据。

**建议的首批实施范围：完成基准后，优先验证全图可见性清零、体素上传尖峰和静态碰撞树重复构建。** 若测量表明它们并非主要开销，则按数据调整排序。真正的成功标准是同等玩法与画质下，卡顿减少、响应稳定、资源可控。

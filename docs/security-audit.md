# 安全边界

## 结论

本地部署的安全重点是密钥、身份 API、服务暴露边界和不可信地图内容，而不是前端界面隐藏。

- DTS 不构成沙箱：客户端脚本仍在玩家浏览器执行，可被查看和篡改。
- 不使用平台域名白名单：URL 只接受合法 HTTP(S)，拒绝脚本/文件协议、控制字符和 URL 凭据。
- 前端隐藏按钮不作为授权依据：所有敏感 API 在服务端验证身份、角色和权限。
- 玩家与后台管理员使用独立账号、会话和 Cookie；服主只能通过服主密钥取得临时会话。

不要在客户端脚本、地图资源、日志或 Release 中存放密码、Cookie、数据库连接串、API Key 或服主密钥。Play 与登录门户公开时必须使用 HTTPS；开放 Creator/VOXA 时还要限制访问来源、创作者身份和具体创作权限。

## 已实施控制

- 玩家密码使用带随机 salt 的 scrypt 摘要；普通玩家单设备会话，后台管理会话独立且更短。
- 登录门户在服务端持有 Player Service API Key；浏览器只得到 `HttpOnly` 会话 Cookie。
- Creator、VOXA、Play 管理和玩家管理 API 分别校验部署模式、Origin、会话及具体权限。
- 地图包导入前可审查代码、图片和音频；审查不执行脚本，安装和地图组发布保持原子性。
- 启动器不会回显已保存密钥；Linux Web 管理端使用独立令牌、固定服务白名单和固定 Docker 参数。

## 仍需由部署者负责

- 使用独立随机密钥、受控 PostgreSQL 账号、TLS、备份和防火墙；不要公开数据库、Redis 或 Docker Socket。
- 只从可信来源导入地图包，并把客户端脚本和资源视为可查看、可修改的不可信内容。
- 正式发行应完成 Windows/macOS 代码签名、公证、校验和验证，并在干净环境执行一次完整安装测试。
- Creator/VOXA 公网模式不是默认安全配置；无法提供 HTTPS、VPN/访问控制和可信创作者账号时，应保持本机模式。

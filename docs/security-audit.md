# 安全边界

## 结论

本地部署的安全重点是密钥、身份 API、服务暴露边界和不可信地图内容，而不是前端界面隐藏。

- DTS 不构成沙箱：客户端脚本仍在玩家浏览器执行，可被查看和篡改。
- 不使用平台域名白名单：URL 只接受合法 HTTP(S)，拒绝脚本/文件协议、控制字符和 URL 凭据。
- 前端隐藏按钮不作为授权依据：所有敏感 API 在服务端验证身份、角色和权限。
- 玩家与后台管理员使用独立账号、会话和 Cookie；服主只能通过服主密钥取得临时会话。

不要在客户端脚本、地图资源、日志或 Release 中存放密码、Cookie、数据库连接串、API Key 或服主密钥。Play 与登录门户公开时必须使用 HTTPS；开放 Creator/VOXA 时还要限制访问来源、创作者身份和具体创作权限。

### 已修复发现：VOXA 匿名资产访问

修复前，VOXA 的只读接口只检查本机来源/CORS，没有验证玩家身份。匿名本机请求可以枚举模型元数据，并根据返回的内容哈希读取模型工程 Blob；`default-skin` 的 PUT 也缺少身份校验。如果 VOXA 被错误反代或公开，这会直接升级为远程创作资产泄露与未授权修改。

修复后的控制如下：

- 模型清单、详情和 Blob 要求当前账号具有创作权限，并至少拥有 `projects.edit` 或 `models.manage`。
- 模型快照和工程导出要求 `models.manage`。
- 默认皮肤读取和修改要求 `projects.edit`。
- Creator 的模型代理会向 VOXA 转发当前玩家会话，由 Player Service 再次实时验证权限。
- VOXA 仍保留 CORS 和回环地址绑定作为纵深防御，但不再把它们当作身份认证。

相关回归测试覆盖匿名身份、权限不足、创作权限撤销、正确模型管理权限和 Creator 代理身份转发。Creator 与 VOXA 生产镜像均完成重建，并使用相同攻击请求完成容器级复测。

## 已实施控制

- 玩家密码使用带随机 salt 的 scrypt 摘要；普通玩家单设备会话，后台管理会话独立且更短。
- 已绑定设备的玩家会话必须同时携带原设备 Cookie；仅窃取 session Cookie、设备 Cookie 缺失或不匹配时都会撤销该会话。
- 玩家登录同时按来源 IP、目标账号和 IP+账号组合持久限流；成功登录只清理当前账号相关桶，并只撤销本次成功尝试对 IP 桶的计数，不能再用其他账号清空既有失败记录。
- 登录门户在服务端持有 Player Service API Key；浏览器只得到 `HttpOnly` 会话 Cookie。
- Creator、VOXA、Play 管理和玩家管理 API 分别校验部署模式、Origin、会话及具体权限。
- 地图包导入前可审查代码、图片和音频；审查不执行脚本，安装和地图组发布保持原子性。
- 启动器不会回显已保存密钥；Linux Web 管理端使用独立令牌、固定服务白名单和固定 Docker 参数。
- PostgreSQL 是永久业务数据源；Redis 与 `box-play-runtime-cache` 只保存可过期或可再生成数据，避免缓存成为权限或存档的唯一依据。

### 2026-09-11 玩家账号接管复核

后续复核发现并修复两条账号接管路径：设备绑定校验曾在请求缺少设备 Cookie 时错误放行；玩家登录限流曾只按 IP 计数，并允许任意账号成功登录后清空整个 IP 桶。修复后增加了缺失/错误设备 Cookie、自有账号清零绕过、跨 IP 猜测同一账号，以及可信登录门户转发真实玩家 IP 的回归测试。

这些控制不能保护纯 HTTP 上传输的密码、会话 Cookie 或服主密钥。Play、Player Service 和登录门户离开完全可信的隔离网络时仍必须使用 HTTPS 或受控 VPN。

## 仍需由部署者负责

- 使用独立随机密钥、受控 PostgreSQL 账号、TLS、备份和防火墙；不要公开数据库、Redis 或 Docker Socket。
- 只从可信来源导入地图包，并把客户端脚本和资源视为可查看、可修改的不可信内容。
- 正式发行应完成 Windows/macOS 代码签名、公证、校验和验证，并在干净环境执行一次完整安装测试。
- Creator/VOXA 公网模式不是默认安全配置；无法提供 HTTPS、VPN/访问控制和可信创作者账号时，应保持本机模式。
